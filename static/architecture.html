02The email component

Five things that happen in the app cause mail to go out on their own. Nobody presses a send button, and no request ever waits for a mail server.

Who gets mailed, and when

TriggerClientProviderMessage kinds
An account is created ✓ the new user, whoever they are welcome
A client books a slot ✓ confirmation ✓ heads-up booked_client · booked_provider
An appointment is cancelled ✓ notice ✓ notice cancelled_client · cancelled_provider
A provider marks one complete ✓ thank-you — completed_client
REMINDER_HOURS_BEFORE the start (default 24 h) ✓ reminder ✓ reminder reminder_client · reminder_provider

What happens when one is triggered

01
Trigger
A route calls notifications.notify_booked() and friends — a side effect that swallows its own errors.
02
Render
One description of the message produces both halves — plain text and styled HTML — so they can't drift apart.
03
Claim
A row is inserted in email_log. The unique index is the gate: if somebody already claimed this message, we stop here.
04
Queue
The message goes to a background worker thread. The HTTP request returns now — it never waits.
05
Deliver
Over SMTP — or printed to the server log when SMTP_HOST is unset, which is the local default.
06
Record
The row is marked sent, or failed with the error — and a failed row is retried by the next scan.
The unique index is the whole de-duplication story. email_log (appointment_id, kind, recipient) is unique, so two overlapping reminder scans, a double-clicked button, or four web workers running at once all collapse into exactly one message per person per reason.

The reminder loop

every REMINDER_SCAN_MINUTES
Scheduler thread
A daemon thread started by the app factory. Under Flask's reloader only the child process owns it, so it never runs twice.
↓
send_due_reminders()
One SQL window query: confirmed appointments whose date || ' ' || start_time falls between now and the cutoff.
↓
Straight into the pipeline above
Claim, queue, deliver, record — the same six steps, with the same guarantee that nobody is reminded twice.
Prefer cron? Set REMINDERS_ENABLED=0 and point it at POST /api/admin/emails/run-reminders instead. Same function, same guarantees.

How it holds up

  • Nothing blocks on the mail server. Delivery happens on a worker thread; a refused SMTP connection is a logged failed row, never a 500 for the person who just booked.
  • Nobody is mailed twice. The claim-before-send pattern plus a unique index, rather than a flag someone has to remember to check.
  • Failures come back. A failed row is re-claimed by the next scan, so a mail outage delays reminders instead of swallowing them.
  • Zero setup locally. No SMTP server? The message prints to the terminal running python app.py, so the whole flow is watchable on a laptop.
  • No new dependencies. smtplib and email.message from the standard library — the deploy story doesn't change.
  • Visible. Admins get an Email log view: what was sent, to whom, whether it landed, plus a test-send button for checking credentials.

07What was verified

The email component was exercised end to end against a throwaway database and a fake SMTP server, not just read over.

Checks that passed

  • A full run — register → book → reminder scan → complete → cancel — produced exactly the 11 expected email_log rows, all sent.
  • A second reminder scan queued 0: nobody is reminded twice.
  • Multipart text + HTML confirmed on the wire against a fake SMTP server, with correct From, To, and Auto-Submitted headers.
  • Unreachable SMTP → row marked failed → retried on the next pass → suppressed once sent, leaving one row.
  • A non-admin gets 403 from /api/admin/emails.
  • Exactly one mailer worker and one scheduler thread, no duplicates.

Fixes made along the way

  • db.insert() — the booking route relied on lastrowid, which is None on Postgres. Now uses RETURNING id there.
  • db.rollback() — Postgres refuses every further statement on a connection after an error, so the IntegrityError branches need it.
  • JWT sub must be a string. PyJWT ≥ 2.10 rejects the integer, so every authenticated request was failing with "Invalid token" until auth.py encoded it as text.
